> Статус: частичный архитектурный аудит по чтению исходников. Это не реализация. Исходный код не изменялся.

## 1. Почему HTML должен быть отдельным типом страницы

HTML-панель должна участвовать в существующей системе страниц: открываться, закрываться, переключаться, отображаться в обзоре и иметь собственную идентичность. Поэтому её нельзя реализовывать как обычный Android-виджет или маскировать под Terminal.

Нужен отдельный `PageKind.HTML` и явные правила для него во всех местах, где тип страницы влияет на поведение интерфейса.

## 2. Почему недостаточно добавить HTML в PageKind

`PageKind` используется не только как метка. От него зависят:
- выбор комнаты (`hasOwnRoom()`, `roomKind()`);
- сторона размещения (`side()`);
- ключи оформления и раскладки;
- подписи и пиктограммы переключателя;
- тип карточки обзора;
- идентификаторы страниц, вычисляемые через ordinal.

`HTML` следует добавлять в конец enum: `PaneWallLayout.kindPageId()` строит kind-only ID с использованием `kind.ordinal()`. Вставка нового значения между существующими может изменить ID уже имеющихся типов.

Одновременно требуется явно определить, должна ли HTML-панель иметь собственную комнату или использовать комнату Terminal. Это решение нельзя оставлять неявному поведению методов по умолчанию.

## 3. Жизненный цикл WebView — главный риск

`Page.offFront()` означает уход страницы с переднего плана, а не окончательное удаление. `Pages.remove()` удаляет страницу из реестра, но применённая страница может оставаться в `mApplied` и позднее получить `offFront()`.

Следовательно:
- нельзя вызывать `WebView.destroy()` в `offFront()`;
- нельзя считать удаление из реестра доказательством, что View уже отсоединена от родителя;
- нельзя уничтожать WebView до завершения перехода старой страницы и отсоединения её View;
- окончательное освобождение должно быть отдельной идемпотентной операцией, выполняемой на UI-потоке после безопасного отсоединения.

Тест `PagesTest.aRemovedFrontStillGetsItsOffFront()` подтверждает, что удалённая страница может позднее получить `offFront()`.

## 4. Почему onRemoved() сам по себе не является безопасной точкой уничтожения

`WallPagesStore.edit()` сначала вызывает `replace()`, а `replace()` синхронно уведомляет слушателей через `onChanged()`. Только после этого при окончательном удалении вызывается `onRemoved()`.

`transform()` также сначала публикует новое состояние через `replace()`, затем уведомляет об окончательно исчезнувших страницах.

Поэтому при удалении контроллер уже может начать убирать страницу из своей регистрации до вызова `onRemoved()`. Кроме того, View может всё ещё находиться в иерархии стены, а объект страницы — ожидать `offFront()`.

Вывод: `onRemoved()` — сигнал о том, что удаление стало окончательным, но не гарантия, что WebView уже можно уничтожать. Нужна координация между хранилищем страниц, контроллером стены, фактическим отсоединением View и lifecycle `Pages`.

## 5. Регистрация и владение View

`PaneWallController` использует отдельные пути регистрации Home, Display, Terminal и Assistant. Универсального HTML-регистратора нет. Для HTML понадобится явная регистрация/фабрика и синхронизация с `WallPages`.

`PaneWallLayout` хранит View по `PageKind`, но `setPageView(kind, null)` очищает регистрацию и связанные wall bookkeeping; это само по себе не гарантирует вызов `removeView()` у старого View. Отсоединение от родителя и удаление из карты — разные действия.

Следовательно, владелец HTML-страницы должен однозначно отвечать за attach/detach и окончательное освобождение WebView. Нельзя полагаться только на `setPageView(kind, null)`.

## 6. Найденные места с fallback-поведением, которое сломает HTML-интеграцию

### Переключатель и карточки

- `PageBarModel`: `kindNames` — массив с четырьмя именами, индексируемый по ordinal. Требуется добавить имя HTML и проверить все обращения по ordinal.
- `PageGlyphSlots`: неизвестный тип попадает в default-ветку с glyph Assistant. Для HTML нужна отдельная ветка.
- `PageOverviewPages.cardKind()`: неизвестный тип попадает в Terminal. Для HTML нужна явная классификация.
- `PageOverviewPages` и `PageOverviewView`: текущие наборы и действия обзора явно перечисляют существующие типы; HTML нужно включить отдельным решением.
- `PageOverviewAddPolicy` и `PageOverviewPolicy`: правила доступности добавления и действий должны знать про HTML.

### Раскладка и оформление

- `LayoutKind.of()` и `pageKind()` используют fallback на Terminal; требуется решить, получает ли HTML собственную раскладку или наследует Terminal.
- `DressResolver.dressKindOf()` по умолчанию относит неизвестный тип к Terminal.
- `WallRow.halfOf()` по умолчанию размещает неизвестный тип на стороне Terminal.
- `PlaceLayoutStore.shownPageId()` явно знает Home, Display и Assistant, а неизвестные типы считает Terminal.
- `PlaceLayoutStore.kindShowsByDefault()` по умолчанию применяет к любому не-Home типу набор Terminal. Это может быть допустимым наследованием, но должно быть осознанным и покрытым тестами.

### Размещение и ключи

- `WallKeys.kinds()` получает типы из расположения страниц; необходимо проверить, должна ли HTML участвовать во всех сценариях клавиш и переходов.
- `WallPages.displayName()` и `startIn()` явно обрабатывают существующие типы; для HTML нужно проверить пользовательское имя и начальное размещение.
- `WallPages` имеет специальные ограничения уникальности для Terminal и Assistant. Нужно определить, допускается ли несколько HTML-страниц.

## 7. Совместимость сохранённого состояния

`WallPagesStore` сериализует тип как `p.kind.name()`, а при чтении использует enum. Текущая версия хранилища — version 2. Добавление нового enum-значения не обязательно требует повышения JSON version, если формат записи не меняется.

Старая версия приложения не знает `HTML`. При чтении такого состояния она может признать его нечитаемым. В коде предусмотрено сохранение исходного unreadable JSON и memory-only режим, чтобы старое приложение не затёрло данные нового формата. Нужен тест downgrade/upgrade: старый клиент не должен уничтожить сохранённую HTML-страницу.

## 8. Рекомендуемая граница MVP

Предлагаемая первая версия:
- отдельная HTML-страница в существующей системе страниц;
- локальный HTML-контент, не универсальный браузер;
- WebView как содержимое страницы;
- обычное переключение без уничтожения WebView;
- сохранение состояния WebView при временном уходе со страницы;
- окончательное освобождение только после безопасного detach;
- Back сначала обрабатывает историю WebView, если она есть, иначе передаётся обычной навигации стены.

Не включать в первый этап:
- произвольную навигацию по интернету;
- широкие разрешения `file://` и `content://`;
- App Mirror / MediaProjection;
- сложное восстановление WebView после убийства процесса;
- переработку `TerminalPaneController`.

Это предлагаемые ограничения MVP, а не уже утверждённые требования.

## 10. Что ещё не доказано и требует проверки

1. Полная цепочка создания и регистрации страниц в `TermuxActivity`.
2. Кто фактически владеет HTML View при смене `PaneWallController.setPages()`.
3. Как именно `PaneWallLayout` отсоединяет старые View в каждом переходе.
4. Все ordinal-индексированные массивы и switch/default по `PageKind`.
5. Полный набор unit/instrumentation тестов для overview, page bar, layout и wall lifecycle.
6. Нужна ли HTML-панели отдельная настройка chrome/room либо достаточно наследования Terminal.

## 11. Итоговое архитектурное решение на текущем этапе

Не начинать реализацию с создания WebView. Сначала зафиксировать контракт владения:

- кто создаёт HTML page и её View;
- кто удерживает WebView при временном переключении;
- кто отсоединяет View;
- кто и в какой момент вызывает одноразовый final release;
- как undo pending removal сохраняет страницу живой.

После этого можно добавлять `PageKind.HTML` и проходить по потребителям enum, закрывая каждый fallback явным поведением и тестом.
