# HTML Native Panel — исследовательский отчёт и передача работы

Дата фиксации: 2026-11-28

## 0. Назначение документа

Этот документ фиксирует результаты архитектурного исследования HTML Native Panel в Termux Launcher.

**Распределение работы между моделями:**

- Исследовательская модель: изучает существующую архитектуру, читает исходники и тесты, проверяет зависимости, выявляет риски, готовит архитектурные выводы и план работ.
- Модель реализации: получает исследовательский отчёт, предлагает и выполняет изменения исходников в согласованных границах.
- Модель проверки: независимо анализирует diff, проверяет lifecycle, совместимость, тесты и соответствие архитектурным решениям.

Исследовательская модель не должна самостоятельно начинать реализацию, пока пользователь явно не поручит это. Её задача — подготовить достоверную техническую основу для следующих моделей.

Этот документ не является спецификацией, окончательно утверждённой пользователем. Предложения и нерешённые вопросы помечены отдельно.

## 2. Цель функции

Добавить HTML-панель как полноценную нативную страницу существующей системы Termux Launcher.

Ожидаемая базовая функциональность:

- HTML/CSS/JavaScript отображаются в Android WebView;
- страница участвует в существующей системе страниц;
- её можно открыть, закрыть и переключить;
- обычное переключение не уничтожает WebView;
- состояние страницы сохраняется при временном уходе с неё;
- окончательное удаление корректно освобождает ресурсы;
- существующие Terminal, Assistant, Display и Home продолжают работать.

HTML-панель не должна быть замаскирована под Android Widget, Terminal или Display.

App Mirror, MediaProjection и интерактивное зеркалирование не входят в базовый MVP.

## 3. Подтверждённые архитектурные факты

### 3.1. Контракт Page

Файл:

`app/src/main/java/com/termux/app/page/Page.java`

Страница предоставляет:

- `kind()`;
- `side()`;
- `view()`;
- `rest()`;
- `onFront()`;
- `offFront()`;
- `onBack()`;
- необязательный `declareGlass()`.

Общего callback окончательного уничтожения страницы в текущем контракте нет.

### 3.2. Pages: удаление не равно уничтожению

Файл:

`app/src/main/java/com/termux/app/page/Pages.java`

`Pages.remove(pageId)` удаляет страницу из `mPages` и `mStops`, но не гарантирует немедленный вызов `offFront()`.

Применённая страница может оставаться в `mApplied`. При последующем переходе она может получить `offFront()` уже после удаления из реестра.

Тест:

`PagesTest.aRemovedFrontStillGetsItsOffFront()`

подтверждает такое поведение.

**Вывод:** `offFront()` — событие ухода с переднего плана, а не окончательное уничтожение страницы.

WebView нельзя уничтожать при обычном `offFront()`.

### 3.3. Pages.onBack()

`Pages.onBack()` сначала передаёт Back текущей странице через её `onBack()`, затем использует стандартный возврат на Home, если страница не обработала событие.

Для HTML логика должна быть следующей:

1. Проверить, есть ли история WebView.
2. Если есть — перейти назад внутри WebView и обработать Back.
3. Если истории нет — вернуть управление обычной навигации Pages.

Не следует вводить второй глобальный обработчик Back без необходимости.

### 3.4. PaneWallController

Файл:

`app/src/main/java/com/termux/app/wall/PaneWallController.java`

Существуют отдельные механизмы регистрации:

- Home: `setHomePageFactory()`;
- Display: `setDisplayPageFactory()`;
- Terminal: `setTerminalStops()`;
- Assistant: отдельная синхронизация страницы.

Универсального механизма HTML-регистрации нет.

`refreshPages()` и синхронизация зарегистрированных страниц связывают `WallPages` с `Pages`, но не заменяют управление жизненным циклом View.

Для HTML понадобится собственный путь создания, регистрации, синхронизации и удаления.

### 3.5. PaneWallLayout и владение View

Файл:

`app/src/main/java/com/termux/app/wall/PaneWallLayout.java`

`mPageViews` — `EnumMap<PageKind, View>`.

`setPageView(kind, null)` снимает регистрацию View и очищает связанные wall bookkeeping-данные. Само по себе это не гарантирует `removeView(previous)`.

Таким образом:

- удаление View из карты;
- отсоединение View от родителя;
- окончательное уничтожение WebView

— три разных действия.

Нельзя считать `setPageView(kind, null)` достаточным освобождением HTML-страницы.

### 3.6. WallPagesStore и порядок удаления

Файл:

`app/src/main/java/com/termux/app/wall/WallPagesStore.java`

`edit()` сначала выполняет `replace()`, а `replace()` обновляет состояние и вызывает `onChanged()`. После этого для окончательного удаления вызывается `onRemoved()`.

`transform()` также сначала публикует новое состояние, затем определяет окончательно удалённые страницы.

Pending removal может быть отменён через Undo.

**Вывод:** при временном удалении нельзя уничтожать WebView. Иначе Undo может вернуть страницу без её прежнего состояния.

`onRemoved()` означает окончательное удаление, но сам по себе не доказывает, что View уже отсоединена и что старая страница завершила переход.

### 3.7. Регистрация страниц и ограничение количества View

`PaneWallLayout` хранит одну View на один `PageKind`.

Это подходит для одной HTML-страницы с одним WebView.

Однако `WallPages.add()` допускает несколько страниц новых типов, если для них не установлено специальное ограничение.

Если будет выбрано несколько независимых HTML-страниц, текущей модели `EnumMap<PageKind, View>` недостаточно без дополнительной архитектуры хранения View.

Это один из ключевых нерешённых вопросов.

## 4. Обнаруженные места, требующие HTML-интеграции

### 4.1. PageKind

Файл:

`app/src/main/java/com/termux/app/page/PageKind.java`

Сейчас присутствуют:

- HOME;
- TERMINAL;
- DISPLAY;
- ASSISTANT.

Рекомендация: добавлять HTML последним значением enum.

Причина: `PaneWallLayout.kindPageId()` использует `kind.ordinal()` для kind-only ID. Вставка значения между существующими типами может изменить уже используемые ID.

Нужно явно определить для HTML:

- `side()`;
- `hasOwnRoom()`;
- `roomKind()`;
- участие в wall navigation;
- правила уникальности.

Текущее поведение по умолчанию относит всё, кроме Display, к собственной комнате и стороне Terminal. Это может быть подходящим наследованием, но не должно оставаться случайным следствием fallback.

### 4.2. PageOverviewPages и PageOverviewView

Файлы:

- `wall/PageOverviewPages.java`;
- `wall/PageOverviewView.java`.

`PageOverviewPages.displayPages()` собирает Display и Assistant, но не произвольные новые типы.

`PageOverviewView.reload()` строит ленту из Home, Terminal и списка этих дополнительных страниц.

`cardKind()` для неизвестного типа использует fallback на Terminal.

Следствия:

- HTML не появится в обзоре автоматически;
- HTML может получить неправильную классификацию карточки;
- действия добавления и удаления должны быть расширены;
- модель карточек должна явно знать HTML.

Не следует представлять HTML как Display только ради попадания в существующий список.

### 4.3. PageOverviewAddPolicy и PageOverviewPolicy

Файлы:

- `wall/PageOverviewAddPolicy.java`;
- `wall/PageOverviewPolicy.java`.

Текущие правила явно ориентированы на Home, Terminal, Display и Assistant.

Для HTML нужно определить:

- доступность добавления;
- возможность нескольких HTML-страниц;
- стартовое размещение;
- правила удаления;
- отображение в обзоре.

### 4.4. PageBarModel и PageGlyphSlots

Файлы:

- `wall/pageswitch/PageBarModel.java`;
- `wall/pageswitch/PageGlyphSlots.java`.

`PageBarModel` использует массив названий с четырьмя элементами и обращается к нему по `ordinal()`.

Добавление HTML без обновления массива приведёт к выходу за границы.

`PageGlyphSlots` для неизвестного типа использует default-ветку Assistant.

Нужно добавить название и отдельную пиктограмму HTML, проверить все ordinal-индексированные структуры и тесты.

### 4.5. Раскладка и оформление

Файлы:

- `place/layout/LayoutKind.java`;
- `chrome/DressResolver.java`;
- `place/PlaceLayoutStore.java`;
- `wall/WallRow.java`.

Текущие fallback-поведения:

- `LayoutKind.of()` относит все не-Home типы к Terminal;
- `DressResolver.dressKindOf()` также использует Terminal для остальных типов;
- `WallRow.halfOf()` относит неизвестный тип к стороне Terminal;
- `PlaceLayoutStore.shownPageId()` для неизвестного типа возвращает Terminal;
- `PlaceLayoutStore.kindShowsByDefault()` применяет к не-Home типам правила Terminal.

Возможно, HTML действительно должен наследовать Terminal chrome и layout. Это допустимое решение MVP, но необходимо явно закрепить его и покрыть тестами.

### 4.6. WallKeys и WallParallax

Файлы:

- `wall/WallKeys.java`;
- `wall/WallRow.java`;
- `wall/WallParallax.java`;
- `wall/PaneWallController.java`.

`WallKeys.kinds()` получает типы из расположения страниц. Требуется проверить, как HTML должен участвовать в клавишах и переходах.

В расчёте порядка страниц `PaneWallController` есть специальные ветки для Display, Assistant и Home. Неизвестный тип может попасть в ветку Terminal.

`WallParallax.rowIndex(PageKind, ...)` также использует Terminal как fallback для неизвестного типа.

Нужно явно включить HTML в расчёт позиции и порядка либо сознательно закрепить наследование Terminal.

### 4.7. WallPages

Файл:

`wall/WallPages.java`

Нужно проверить и расширить:

- `displayName()`;
- `startIn()`;
- правила множественности;
- создание и идентификацию HTML;
- восстановление сохранённых страниц.

Сейчас Terminal и Assistant имеют специальные ограничения уникальности. Для HTML политика ещё не определена.

### 4.8. Сохранение и downgrade

Файл:

`wall/WallPagesStore.java`

Тип страницы сериализуется через `p.kind.name()`.

При чтении enum-значение должно быть известно текущей версии приложения.

Если более новая версия сохранит HTML, старая версия приложения может не прочитать это состояние.

В коде предусмотрены `unreadable()` и `useForThisRun()` для сохранения несовместимого сохранённого состояния без перезаписи его текущим запуском.

Нужны тесты:

- сохранение HTML;
- восстановление HTML;
- чтение старой версии формата;
- downgrade на сборку без HTML;
- отсутствие перезаписи неизвестного JSON;
- повторное открытие новой версии и восстановление данных.

Повышать JSON version только из-за добавления enum не обязательно, если структура формата не меняется. Но совместимость нужно доказать тестами.

## 5. Отдельные риски WebView

### 5.1. Lifecycle

Нужно разделить:

- создание страницы;
- attach View;
- временный detach;
- повторный attach;
- временное удаление с Undo;
- окончательное удаление;
- final release.

Рекомендуемая модель:

- обычный `offFront()` не уничтожает WebView;
- временное удаление сохраняет объект и состояние;
- Undo возвращает ту же страницу и View;
- окончательное удаление помечает страницу для освобождения;
- final release происходит после завершения перехода и detach;
- освобождение идемпотентно;
- `WebView.destroy()` вызывается на UI-потоке после detach.

В текущем `Page` нет callback, который однозначно означает окончательное уничтожение.

Архитектурное решение по этому контракту нужно принять до реализации.

### 5.2. Back и клавиатура

`Pages.onBack()` предоставляет естественную точку для обработки истории WebView.

Однако необходимо проверить `TermuxActivity.dispatchKeyEvent()` и маршрутизацию клавиш, чтобы WebView с фокусом корректно получал ввод и не ломал Terminal.

Особенно проверить:

- аппаратную клавиатуру;
- Enter и навигационные клавиши;
- Back;
- возврат фокуса после переключения;
- поведение при открытой системной клавиатуре.

### 5.3. Снимки в Page Overview

`PageOverviewView` использует получение изображений карточек, включая `PixelCopy` и отрисовку View.

Для WebView требуется проверить:

- корректность снимка;
- пустую или чёрную карточку;
- поведение при временном detach;
- отсутствие лишнего обновления и перерисовки;
- отсутствие конфликтов с аппаратным ускорением.

### 5.4. Безопасность локального HTML

Рекомендации для MVP:

- только локальный HTML;
- не делать универсальный браузер;
- ограничить разрешённые схемы и URL;
- не включать широкие разрешения доступа к файловой системе;
- не разрешать произвольную навигацию;
- не добавлять универсальный JavaScript bridge;
- включать JavaScript только если он действительно нужен для содержимого;
- рассмотреть `WebViewAssetLoader` для локального контента;
- не разрешать mixed content без доказанной необходимости.

В проекте на момент исследования не обнаружена существующая реализация WebView или явная зависимость `androidx.webkit`.

В `app/build.gradle` обнаружены параметры Android:

- minSdk 26;
- targetSdk 28.

Нужно перепроверить зависимости и поведение на реальном устройстве при начале реализации.

## 6. Предлагаемый MVP — не утверждённая спецификация

Предварительное предложение:

- отдельный PageKind.HTML;
- отдельная HTML Page и View;
- локальный HTML;
- WebView как содержимое страницы;
- наследование Terminal chrome и стороны;
- сохранение WebView при переключении;
- корректное временное удаление и Undo;
- отдельный final release;
- Back сначала обрабатывает историю WebView;
- без App Mirror и MediaProjection;
- без универсального браузера;
- без переработки TerminalPaneController;
- без сложного восстановления WebView после убийства процесса на первом этапе.

**Количество HTML-страниц не утверждено.**

Одна HTML-страница естественно соответствует текущей модели одной View на PageKind.

Несколько независимых HTML-страниц требуют отдельного дизайна: например, page-id keyed View registry вместо одного `EnumMap<PageKind, View>`.

Нельзя выбирать один из вариантов без явного решения пользователя.

- точными файлами;
- предлагаемыми интерфейсами;
- lifecycle-инвариантами;
- последовательностью реализации;
- обязательными тестами;
- запретами на ненужный рефакторинг.

До завершения этих этапов не начинать массовые изменения исходников.

---

## 10. Инварианты, которые реализация обязана сохранить

1. `offFront()` не означает destroy.
2. Временное удаление с Undo не уничтожает HTML-состояние.
3. `setPageView(null)` не считается гарантированным detach.
4. WebView не уничтожается, пока он присоединён к родителю.
5. Final release выполняется один раз и на UI-потоке.
6. Back сначала учитывает историю HTML, затем стандартную навигацию.
7. HTML не маскируется под Terminal, Display или Android Widget.
8. Существующие Terminal, Assistant, Display и Home не должны менять своё поведение.
9. Добавление enum не должно незаметно ломать ordinal-based структуры.
10. Сохранённые данные неизвестных старой версии типов не должны перезаписываться.
11. Нельзя включать широкие WebView-разрешения без обоснованной необходимости.
12. Не менять TerminalPaneController ради HTML без доказанной необходимости.

## 11. Инструкция следующей модели

Этот документ — исследовательская база, а не разрешение на реализацию.

Следующая модель должна:

- прочитать этот документ целиком;
- сверить состояние ветки и коммит;
- не считать предположения утверждёнными требованиями;
- не переписывать архитектуру стены;
- не менять TerminalPaneController без необходимости;
- сначала предложить план и интерфейсы;
- отдельно описать lifecycle и Undo;
- запросить подтверждение только по решениям, которые нельзя вывести из существующего кода.

Исследовательская модель продолжает читать репозиторий и обновлять технические выводы. Реализация выполняется отдельной моделью после передачи ей согласованной спецификации.
